What actually happened

1 · DefineA typed OptimizationJob requests 4 trials and a loss objective.
2 · SuggestOptuna Random search selects a learning rate.
3 · TrainTrainer + JobSet start a CPU Pod. It fits weight and bias for 40 epochs.
4 · ReportThe Kubeflow SDK pushes val_loss over authenticated HTTPS.
5 · CompareThe controller records the successful trial with the lowest loss.

One trial runs at a time. Each completion makes room for another until the four-trial budget is exhausted. Reconciliation reacts to Kubernetes resource changes; it is not one long training function inside the controller.

See the learning, not just the score

The same seeded dataset and starting weights keep the comparison fair. A learning rate controls how far each gradient update moves the model. Choose a trial to inspect its measured validation-loss curve.

Model: prediction = weight × x + bias. Target data: y ≈ 2x + 1. Each trial uses 64 training samples and 64 separate validation samples. MSE means average squared prediction error; lower is better.

What the baseline produced

The first development session created a clean Git repository, pinned the upstream source and verified existing behavior: 20 top-level Go tests, 50 SDK optimizer tests and 3 smoke-runner guard tests passed. That was a tested starting point.

This demo adds the missing visible proof: an actual cluster, the upstream controller, four TrainJobs, real model fitting, SDK metric delivery and a checked best result.

What remains unfinished

GPU execution and shared model/dataset initialization were not demonstrated. The existing OptimizerClient still submits legacy Experiments, so this demo submits the typed OptimizationJob directly with kubectl.

The controller, JobSet and Optuna are reused upstream software. This demo does not claim those components were newly implemented or that a four-trial run proves crash recovery or production security.
